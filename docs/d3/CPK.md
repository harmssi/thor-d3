# Diablo III (Switch): архивы CPK

Формат — собственный консольный архив Blizzard (не CRIWARE: у CRI магия `"CPK "`). Ридер: `tools/d3cpklib.py` — вендорная копия
`cpklib.py` из [D3CPKUnpack](https://github.com/RedMadKnight/D3CPKUnpack) (MIT, Krzysztof Janiszewski, коммит 9fa02146, лицензия рядом в
`tools/d3cpklib.LICENSE`), без правок. Фронтенд: `tools/d3_cpk.py`. Описание ниже сверено с нашими файлами (v1441792 = 2.7.7), см. «Проверка».

## Команды

```sh
export PYTHONUTF8=1
python tools/d3_cpk.py info    work/romfs/CPKs/CoreCommon.cpk          # поля заголовка, битовые ширины, сектора
python tools/d3_cpk.py verify  work/romfs/CPKs/*.cpk                    # CRC32 секторов + каждый чанк распаковывается в свой размер
python tools/d3_cpk.py list    work/romfs/CPKs/ClientCommon.cpk 'Shaders/*.shd'   # name, size, comp_est, offset, copies
python tools/d3_cpk.py extract work/romfs/CPKs/Act1.cpk out/ '*.tex'
python tools/d3_cpk.py mlist   work/romfs '*.shd'                       # слитый вид: имя, размер, какой архив его даёт
python tools/d3_cpk.py mextract work/romfs work/cpk-shaders '*.shd'     # + _sources.tsv
python tools/d3_cpk.py scan    work/romfs 34127698                      # какие члены содержат байтовый шаблон
```

Маска — fnmatch без учёта регистра по имени с `/`. При извлечении `\` -> `/`, `|` (локализованные имена вида `x.stl|enUS`) -> `__`.
`comp_est` — оценка сжатого размера: байты чанков каждого задетого сектора, пропорционально доле распакованного диапазона (у файла нет
собственного сжатого блока: сжимается общий поток).

## Устройство

Все числа little-endian (на Switch магия на диске `d4 c3 b2 a1`). Битовые таблицы читаются MSB-first внутри байта, каждая начинается с границы байта.

Заголовок, 0x48 байт (v7):

| off | размер | поле |
|---|---|---|
| 0x00 | 4 | магия 0xA1B2C3D4 |
| 0x04 | 4 | версия = 7 |
| 0x08 | 8 | `decomp_fs` — длина общего распакованного потока |
| 0x10 | 4 | `fmt_const`: 2 — базовые архивы (`header_sector` в единицах `read_sector`), 10 — патчи 2.6.5+ (`header_sector` = прямое смещение) |
| 0x14 | 4 | число файлов (строк SortedFileInfo) |
| 0x18 | 4 | число Locations (= файлам: на Switch копий нет) |
| 0x1C | 4 | `header_sector` -> смещение первого сжатого сектора `first_sec` |
| 0x20..0x34 | 6×4 | битовые ширины: размер файла, число копий, индекс первой Location, Location, cs2do, ds2cs |
| 0x38 | 4 | CRC32 (zlib) всего `data[first_sec:]` |
| 0x3C | 4 | `read_sector` = 0x10000 |
| 0x40 | 4 | `comp_sector` = 0x4000 (ширина слота сжатого сектора) |
| 0x44 | 4 | 0 |

Дальше подряд:
1. **SortedFileInfo** (битовая): на файл `u64 FNV-1a(имя в нижнем регистре)` (basis 0xCBF29CE484222325, prime 0x100000001B3), размер, число копий, индекс первой Location.
2. **Locations** (битовая): смещение копии файла в общем распакованном потоке.
3. **cs2do** (битовая): для каждого сжатого сектора — смещение его данных в распакованном потоке (сектора не обязательно равны 0x4000 после распаковки).
4. **ds2cs** (битовая, для быстрого поиска; ридеру не нужна — хватает бинпоиска по cs2do).
5. Таблица `u32` смещений имён (по одному на файл) + блоб строк, NUL-terminated, путь через `\` (`Shaders\particle_additive.shd`). Имя связывается со строкой SFI через хеш.
6. Выравнивание нулями до `first_sec` (только `fmt_const` 2), затем слоты сжатых секторов по 0x4000 байт.

Слот сектора — цепочка чанков: заголовок 6 байт `u16 decomp_lo, u16 decomp_hi, u16 zsize` + `zsize & 0x7fff` байт данных; `zsize == 0`
завершает цепочку. Данные — **zlib** (других алгоритмов нет, Oodle/LZ4 не используются). Бит `0x8000` в `zsize` — чанк дополнительно
зашифрован потоковым шифром с обратной связью по шифртексту: `p[i] = c[i] ^ (state & 0xff); state = (c[i] << 56) | (state >> 8)`,
начальное состояние 0x873AE8E53C11D761 (одно на все чанки), т.е. ключевой поток = 8 байт константы + сам шифртекст. Последний чанк
сектора обычно обрезан границей слота: распаковывается потоковым `decompressobj` ровно в `decomp` байт. Распакованные секторы
кладутся в общий поток по cs2do; файл = `stream[Location : Location + size]`.

Пустые архивы (`enUS_ClientCommon`, `enUS_CoreCommon`): 0 файлов, один сектор. `*Cutscene.cpk` на Switch — обычные zlib-архивы (`.ogv`).

## Патчи и слитый вид

Игра (main 2.7.7) монтирует `<root>\CPKs` и `\Update\CPKs` перечислением `*.cpk` (функция main+0x74cf70, строка `*.cpk` @ main+0xe0f169),
сортирует имена компаратором main+0x74fff0, который сравнивает «натурально» (main+0x743890: цифровые группы как числа, остальное побайтно),
и открывает каждый по порядку (`%s\%s.cpk`). Порядок патчей поэтому:
`Patch2_6_5 < 2_6_6 < 2_6_7 < 2_6_7a < 2_6_8 < 2_6_9 < 2_6_10 < 2_7_0 < 2_7_1 < 2_7_3 < 2_7_4 < 2_7_5 < 2_7_6 < 2_7_7`
(лексикографически 2_6_10 оказался бы перед 2_6_5). `d3_cpk.py` строит слитый вид: базовые CPKs, затем Update/CPKs в этом порядке;
имя (без учёта регистра — поиск идёт по FNV-1a от нижнего регистра) из более позднего архива заменяет более раннее. То, что выигрывает
поздний архив, — допущение (сама логика поиска по смонтированным архивам не разбиралась), но оно согласуется с назначением патчей; для
шейдеров порядок между патчами не важен: все .shd в 2_6_5/2_6_7/2_6_8 дают одни и те же ключи (2_6_7 и 2_6_8 побайтно равны).
В базовых архивах одни и те же имена встречаются в нескольких CPK (Act4 повторяет 8 191 имя из Act1–3 и т.п.); по данным D3CPKUnpack эти
копии побайтно одинаковы. Строки `\Update2\CPKs`, `update-%d.cpk`, `%s\Update.cpk`, `%s\Locale.cpk`, `PVPCommon.cpk` в main есть, но таких
файлов в RomFS нет.

Итог по RomFS v1441792: 37 архивов (23 базовых `fmt_const` 2 + 14 патчей `fmt_const` 10), 488 722 записи, 1 483 670 чанков (22 294
зашифрованных: CoreCommon, ServerCommon и патчи), распакованный объём 31,5 ГБ; слитый вид — 346 156 имён.

## Проверка

* `verify` по всем 37 архивам (`work/logs/verify_all.txt`): CRC32 секторов совпадает везде, 0 чанков, которые не распаковались или дали
  размер не по cs2do; ни одного имени без строки SFI.
* Все 1 569 файлов `Shaders/*.shd` слитого вида начинаются с SNO-магии 0xDEADBEEF, и каждая найденная в них NVN-секция проходит
  проверки длин (`tools/d3_shader_jobs.py`, 0 проблем).
* `scan` всех членов всех архивов на магию control-секции NVN: только `.shd` (+3 случайных совпадения в FSB5-банках звука).
