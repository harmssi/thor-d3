# Diablo III (Switch 2.7.7) → Android: тач-управление — разбор d2r-mobile и дизайн для D3

Дата: 02.11.2026. Исследование без правок `dm/` и без телефона. Адреса D3 — смещения в `work/exefs-update/main.raw`
(main build-id `2607a74f5df7754cc0357b5df7e496931355d8ca`, SDK 8.2.0). Адреса D2R — смещения образа D2R 3.3.94012 из upstream
`jhaizhou-ops/d2r-mobile` (клон `work/reference/d2r-mobile`, коммит `fae8c68`, v2.2.4).
Новый инструмент: `tools/d3_ui_callbacks.py` → `work/d3-ui-callbacks.tsv` (573 именованных UI-колбэка D3 с адресами).

## TL;DR

* D2R Mobile работает потому, что у D2R на Switch **внутри остался PC-интерфейс** (дерево виджетов с мышиными сообщениями
  `InputMessage`/`MouseMove`/`LeftMouseButtonDown`, JSON-раскладки, общая точка «клик по миру») и игра **сама читает тачскрин**.
  Хост d2r-mobile шлёт мышиные сообщения в корневой виджет, двигает «свободный курсор» геймпада записью в память, вызывает
  игровую функцию клика по миру и подменяет раскладки через overlay-RomFS. Это ~10 тыс. строк кода, завязанных на адреса D2R.
* У D3 на Switch **нет ни тача, ни мыши, ни клавиатуры** в импортах, а UI — консольный, фокусный (кольца/списки, колбэки
  `UIInventory_OnButton1`, `…_OnLeftStick`, `…_OnDPadLeft`). Прямой перенос подхода D2R невозможен.
* Зато у D3 нашлось то, за что можно зацепиться: **таблица имён UI-колбэков** (573 шт., с адресами функций), **менеджер UI**
  с хеш-картой контролов и полем «текущий фокус», функции **`UI_GetControl(UIID*)` = main+0x330000** и
  **`UI_SetFocus(UIID*)` = main+0x327dd0**, **`UI_SetSafeZone` = main+0x3277a0** и пер-экранные `*_Update`-колбэки
  (детектор «какое меню открыто»).
* Рекомендация: **фаза 1 — чистый фронтенд** (Java, без хуков): плавающий стик + «тап-и-держи в мире = идти туда»,
  двойной тап = уклон (флик правого стика), крупные кнопки скиллов/зелья, тач-навигация жестами в меню и ручной переключатель
  режимов. **Фаза 2** — детектор «меню/геймплей» в хосте (чтение фокуса UI-менеджера, затем observation-гейты на `*_Update`).
  **Фаза 3** — «тап по пункту меню = фокус + A» через `UI_SetFocus` после рантайм-дампа контролов. PC-UI D3 не оживлять.

## 1. Как устроен тач в d2r-mobile

### 1.1 Слои

```
Android View (TouchOverlay.java: только рисует; события → nativeEvent)
  └─ touch_android.c → dm_tc_* (ios/Sources/dm_touch_controls.c: общий автомат жестов iOS/Android)
       ├─ кнопки/стик → dm_input_set(): npad-кнопки и стики (hle_hid.c, как настоящий Joy-Con)
       ├─ касания в UI → dm_ui_touch / dm_ui_item_query / dm_ui_drag_* (host/dm_cursor.c, 3392 строки)
       ├─ касание в мире → dm_world.c: вызов игровой функции клика по цели
       └─ сырые точки → hle_touch.c → nn::hid::GetTouchScreenStates (игра читает тач сама)
dm_pad_hook (hle_hid.c fill()) — точка, где весь этот слой «доклеивает» кнопки/стики к состоянию npad каждый раз, когда игра его читает
```

### 1.2 Механизмы (с доказательствами)

| Что | Как сделано в D2R | Где (upstream) |
|---|---|---|
| Сырые касания | D2R Switch сам читает тач (`GetTouchScreenStates`, функция main+0x1b65260, панель 1280×720); хост заполняет `TouchScreenState<16>` с защёлкой Start/End, чтобы короткий тап между двумя опросами не потерялся | `dm/host/hle_touch.c:1-16` |
| Тап по UI | **мышиные сообщения в дерево виджетов**: корень UI = `*(main+0x2f05458)`, сообщение `{FNV1a("InputMessage"), FNV1a("MouseMove"/"LeftMouseButtonDown"/…), payload{x,y,arg}}` отдаётся в `vtable+0x28` корня; имена найдены поиском хешей в инструкциях | `dm/host/dm_cursor.c:538-546, 561-565` |
| Хит-тест | обход дерева: `+8` имя, `+0x50` видим, `+0x58/+0x60` дети; у виджета `vtable+0x48` = «точка во мне?» (упакованные x/y). Классы распознаются по vtable | `dm_cursor.c:124-137, 602-620, 856` |
| Сетки предметов, drag&drop | пишется позиция **свободного курсора геймпада** `main+0x2d128f8/0x2d128fc`, затем подаётся A; очередь «отложенных A», радиус прибытия 4 px, повторы при неудачном «положить», возврат предмета | `dm_cursor.c:28-33, 46-61, 306-380` |
| Тап по NPC/предмету/двери | игровая функция клика `main+0x4ace20(player, action, x, y, flags)` (общая для кнопки A и ЛКМ), цель через слот «назначенная цель» `[mgr+0xd10]`, mgr = `main+0x2acecc()` | `dm/host/dm_world.c:1-8` |
| Автоприцел по тапу | observation-гейт на компаратор кандидатов `main+0x2f7664` (из `main+0x2f70b4`): босс > элита > обычный | `dm/host/hle_target.c:1-12` |
| Движение | виртуальный стик, 60 pt полный ход, мёртвая зона 6 pt; **изометрическая коррекция** (вертикаль ×2), чтобы экранный угол пальца = угол хода | `ios/Sources/dm_touch_controls.c:220-245` |
| Скиллы | кнопка = npad-кнопка; «держи» = держать кнопку; **перетаскивание = направление через правый стик** (мёртвая зона 10 pt), плюс приватный адаптер направления; второй набор = модификатор ZL с опережением | `dm_touch_controls.c:137-161, 163-215`; `hle_private_aim.c:1-11` |
| Сцена: «меню или игра» | observation-гейт на шину UI-сообщений `main+0xb1dc60` (`PanelManager OpenPanel/ClosePanel <имя>`, `FrontEndNavigation ToFrontEnd`) → набор открытых панелей → режим навигации (кнопки пада прячутся) | `dm/host/diag.c` (OBS_UIMSG), `dm_touch_controls.c:735-750` |
| UI под пальцы | **overlay-RomFS** (`DM_ROMFS_OVERLAY`): свои раскладки панелей (префикс `Controller/Console/Switch/` переписывается на тач-каталог, `main+0xb84750`), подсказки геймпада убраны, «Нажми A» → «Двойной тап», нижний HUD v4 из PNG | `dm/host/dm_padmode.c:1-12`, `dm/ios/README.md:84-96` |
| Режимы | тач ↔ геймпад переключаются на лету по последнему источнику ввода (перезагрузка раскладок через фиктивную смену operation mode) | `dm_padmode.c` |

Итог по D2R: тач возможен, потому что (1) игра — порт PC-версии и внутри у неё мышь, (2) UI — дерево именованных виджетов с
хит-тестом, (3) есть overlay файлов игры. Половина работы — надёжность (очереди нажатий, повторы, защёлки).

### 1.3 Что из этого есть в нашем дереве

`dm/host/dm_cursor.c`, `dm_world.c`, `diag.c`, `hle_target.c` и др. лежат в дереве, но для `DM_GAME_DOOM` (а значит и d3)
**не собираются** (`dm/android/CMakeLists.txt:91-100`, явный allowlist; `hle_target.c` исключён). Собирается только
автомат жестов `ios/Sources/dm_touch_controls.c` и `android/touch_android.c`; их вызовы D2R-хоста закрыты заглушками
`dm/host/doom_stubs.c` (`dm_cursor_pending:89`, `dm_ui_item_query:114`, `dm_custom_get:153`). Хук `dm_pad_hook`
ставится для всех игр (`dm/android/front_android.c:42`) и вызывается в `hle_hid.c:425` при каждом чтении npad.
Сейчас D3 рисует `DoomPadView.java` (Joy-Con-подобный пад) и шлёт клавиши/оси через `DmActivity.nativePadKey/nativePadAxes`
(`jni_android.c:429-433`) в канал контроллера. Это и есть точка входа для фазы 1 — без нового C-кода.

## 2. Что есть в D3 (находки)

### 2.1 Ввод
* Импорты hid: только `GetNpadStates` ×5 стилей, `GetNpadStyleSet`, six-axis, вибрация, `ShowControllerSupport`,
  `ShowControllerStrapGuide` (разбор `main.symbols.json`). Тача/мыши/клавиатуры нет.
* Опрос пада: функция **main+0xf7310** (объект пада: `+0` npad id, `+0xc` style set, `+0x18…` кнопки/стики), вызовы
  `GetNpadStates` на 0xf751c/0xf7814/0xf7b38/0xf7e20/0xf8124; её зовут 0xf6f78…0xf85ec (по игроку).
* Строки `BUTTON_1..4, BUTTON_DPAD_*, BUTTON_LEFT/RIGHT_SHOULDER/TRIGGER, BUTTON_TOUCH_PAD, BUTTON_OPTIONS` — общий
  консольный enum (PS4-тачпад — это кнопка, не указатель). `ConsoleDebugController.ui` с контролом `TouchPad` — отладочная
  отрисовка (`UIConsole_TouchPadDebugDraw`, 0x33644c), не путь ввода.
* Уклон: строка раскладки `Console:ControllerLayoutFlickEvade` (`UI/ConsoleControllerLayout_NX64.ui`) — **флик правого стика**.
* Скриптовые «курсоры силы»: `PowerCursorSetToLeftStick`, `PowerCursorSetToRightStick`, `PowerCursorSetToCastTarget` —
  наведение консольных скиллов идёт от стиков/автоцели, отдельного экранного курсора в мире нет.

### 2.2 UI-система D3 (консольная, фокусная)
* **UIID** — 64-битный хеш пути вида `Root.NormalLayer.ConsoleInventoryRing_main.LayoutRoot.InventoryRing.RingGlow.Cursor`:
  `UIID_FromPath` = main+0x347ce0 → 0x347750 (строка из 16 hex-цифр = готовый UIID; иначе нормализация 0x70c0/0x7ab0 и хеш 0x6c90).
  Глобальные хендлы заполняются статическими инициализаторами (пример 0x33b078…0x33b0e0: путь → `0x347ce0` → `0x3474e0`
  `*(dst)=id`). «Пустой» UIID — статик `main+0x1862638` (= -1), возвращает 0x347300.
* **Менеджер UI**: `mgr = *( *(u64*)(main+0x1905620) + 0xb80 )` (GOT `main+0x114a840` → `&g = main+0x1905610`, поле `g+0x10`).
  * `mgr+0x00` → карта контролов `{u32 mask @0; buckets @0x10}`, узел `{next @0; u64 UIID @8; UIControl* @0x10}`,
    индекс = FNV-1a-32 по 4 младшим байтам UIID `& mask` (код 0x330000…0x330078).
  * `mgr+0x50` — **UIID текущего фокуса**.
* **`UI_GetControl(const UIID*)` = main+0x330000** → `UIControl*`; при промахе пишет `"UI ERROR: Failed to find UIID %s"`
  (0xdd5ced) и **падает** (0x3300f0: assert) — из хоста искать в карте самим, не звать вслепую.
* **`UI_SetFocus(const UIID*)` = main+0x327dd0**: если новый ≠ текущему — записывает `mgr+0x50`, у старого контрола зовёт
  `vtable+0x38` (потеря фокуса), у нового `vtable+0x40` (получение). 163 вызова в коде. `Console_YieldFocus` и
  `UIInventory_YieldFocus` (оба = main+0x367110) = `UI_SetFocus(&invalid)`.
* **Таблица именованных колбэков** (то, что раскладки `.ui` вызывают по имени): записи `{char* name; u32 hash; void* fn}`
  по 0x18 байт в .bss (первая таблица с main+0x186f168), заполняются инициализаторами main+0x3c2c20…0x3c9968 и
  0x3c9970…0x3cc27c; `hash` = main+0xa49690 (`h = h*33 + (signed char)c`, с 0). Полный дамп: `tools/d3_ui_callbacks.py`.
  Примеры: `UIInventory_OnButton1` 0x1f6910, `UIInventory_OnLeftStick` 0x1f66f0, `UIInventory_OnDPadLeft` 0x1f6800,
  `UIInventory_Console_Update` 0x1f66b0, `UISkills_Console_Update` 0x381b70, `UIPause_OnUpdate` 0x220f00,
  `UIConsole_MainMenu_OnUpdate` 0x362500, `UIConsole_Options_OnUpdate` 0x20b550, `WaypointMap_OnUpdate` 0x238270,
  `UIConsoleSafeZone_OnButton2` 0x22cfc0, `Console_CloseAll` 0x3c28b0. Экранов с `*_Update` ~45 — это готовый список
  «какое меню сейчас живо» (у HUD геймплея такого колбэка нет).
* Раскладки — бинарные SNO `UI\*.ui` в `ClientCommon.cpk` (400 файлов, 143 `Console*`), якоря `Bottom/Left/Stretch`
  (`ConsoleHUD.ui`). Патчи `Update/CPKs/Patch2_x.cpk` перекрывают члены базовых архивов (`tools/d3_cpk.py mextract`).

### 2.3 Остатки PC-интерфейса (и почему они не спасают)
* В данных лежат PC-раскладки `GameHUDPC.ui`, `Inventory.ui`, `Stash.ui`, `SkillPane.ui`, `SkillBar.ui` (их даже обновляли
  патчи 2.6.5–2.6.8), в таблице колбэков есть `UI_InvOpen_OnClick` 0x3d6500, `UI_StashGrid_OnRightClick` 0x3f6cb0,
  `UI_HUD_ClickPredicate` 0x3d64e0 (**это `return 1`** — заглушка), строки курсоров (`cursor_hand_normal_large` …),
  таблица имён клавиш (`RETURN, F1, MEDIASELECT, Mouse1..Mouse5`), опции `LeftClickToMove`, `RightClickAttack`.
* Но источника мышиных событий нет, а найти/оживить PC-диспетчер (хит-тест + клики + PC-HUD) — отдельный большой реверс без
  гарантии, что консольная ветка его не вырезала. **Не рекомендую** (см. §3, вариант E).

### 2.4 Настройки для «пальцев»
* Масштаба UI/шрифта в консольной D3 нет (нет строк `UIScale/FontScale/TextSize`). Шрифты и так «телевизионные» — на 6.7"
  читаемы.
* Есть **Safe Zone**: опция `ConsoleOptions:SafeZone` (код опций 0x20f0d0), экран `ConsoleSafeZone.ui`,
  `UIConsoleSafeZone_OnButton2` (0x22cfc0) применяет прямоугольник: 4 float из состояния экрана `*(main+0x17ff0f0)+0x18`
  → **`UI_SetSafeZone` = main+0x3277a0(…, l, t, r, b)**, который пишет `{l, t, 1-r, 1-b}` в `obj(0x27a300)+0xa0` и
  переставляет раскладку; поля сохраняются как `flSafeZoneLeft/Right/Top/Bottom` (0x27d3c0).
  Это способ **отодвинуть весь HUD от краёв** под большие пальцы — без правки раскладок.

### 2.5 Чего статикой не узнать (проверить в рантайме)
1. Что лежит в `mgr+0x50` в геймплее (невалидный UIID? HUD?) и в каждом меню.
2. Раскладка `UIControl`: прямоугольник, видимость, родитель/дети, путь/имя; система координат (у PC-D3 UI — 1200 по высоте).
3. Выбирает ли `UI_SetFocus` слот **внутри** кольца/списка (InventoryRing, ItemList) или только целый контрол.
4. На каком потоке вызывается `dm_pad_hook` (нужен поток UI игры для чтения/вызова UI-функций).
5. Стоит ли герой при «зажать скилл + отклонить левый стик» (прицел) или идёт.
6. Видна ли опция Safe Zone в меню Switch-версии.

### A. Геймплей без хуков (фаза 1)

Всё в `DoomPadView.java` (ветка `D3`) или новом `D3TouchView.java` поверх `SurfaceView`; выход — те же
`DmActivity.nativePadKey(PAD_DEVICE, key, down)` и `nativePadAxes(PAD_DEVICE, lx, ly, rx, ry, …)`.

1. **Левый стик** — как сейчас (плавающий в левой нижней четверти), без изменений.
2. **«Тап-и-держи в мире» = движение к точке.** Касание в свободной зоне (не кнопка, не стик, не верхняя полоса меню):
   * якорь героя `H = (0.5·W, hy·H)` (камера D3 центрирует героя; `hy` ≈ 0.5…0.56 — калибруется, настройка в ⚙);
   * вектор `d = P − H`; **перспективная коррекция**: стик = `normalize(dx, −dy / s)`, `s` = видимое сжатие глубины камеры
     (калибровка: толкнуть стик под 45° и померить экранный угол хода по скриншотам: `s = tan(θэкр)`; ожидаем 0.6–0.8);
     аналог `g_iso_fix` D2R (`dm_touch_controls.c:236-242`), только коэффициент не 2:1;
   * модуль: `|d| < r0` (≈ радиус героя, 40 dp) → 0 (не дёргать на месте), дальше полная скорость; палец можно вести —
     направление обновляется каждый кадр; отпускание → стик 0.
   * короткий тап по миру (< 180 мс, сдвиг < 12 dp) = «подойти и взаимодействовать»: 250–400 мс хода к точке, затем
     импульс кнопки взаимодействия/основной атаки (консольная D3 подбирает/говорит/открывает ближайшее в направлении).
     Включаемо настройкой (по умолчанию — только ход), т. к. без хука на цель это эвристика.
3. **Двойной тап по миру = уклон** в сторону точки: импульс правого стика `normalize(dx, −dy/s)` на 100–120 мс (флик —
   `Console:ControllerLayoutFlickEvade`).
4. **Кнопки скиллов**: дуга из 6 круглых кнопок справа (как D2R Mobile/Diablo Immortal) = 6 npad-кнопок, которыми D3 вешает
   скиллы (A/B/X/Y/R/ZR в текущей раскладке игры; переназначение — в Options → Controller игры, `ConsoleOptions:ControllerTab`).
   Удержание = удержание кнопки. Перетаскивание с кнопки (> 10 dp) — **проверить пункт 2.5/5**: если D3 при зажатом
   скилле разворачивает героя левым стиком без шага — подавать направление в левый стик с малым модулем; иначе не делать.
5. **Зелье / портал / карта / меню**: отдельные кнопки (L, D-pad-направления, «−», «+») в верхнем правом углу, крупные.
6. Подписи кнопок — пока текстом (A, X …) или иконками, выбираемыми в ⚙; чтение реальных иконок скиллов из игры —
   только после реверса HUD (не в этой фазе).
7. Мультитач: стик + кнопки + «держи в мире» независимы по pointer id; «держи в мире» и левый стик — оба пишут левый стик,
   приоритет у стика.

Риски: калибровка `hy`/`s` зависит от зума камеры (D3 приближает в городе? — проверить в Тристраме и в данже);
тап-взаимодействие может атаковать вместо разговора — поэтому выключено по умолчанию.

### B. Детектор «меню / геймплей» (фаза 2)

Цель: в геймплее — боевой пад (A), в меню — навигационный (C1/C2), без ручного переключения.

* **B0 (уже сейчас)**: ручная кнопка «режим» на паде + запоминание. Нужна всегда как запасной путь.
* **B1 — чтение фокуса** (дёшево, без правки NSO): в `dm_pad_hook` (D3-ветка `front_android.c`/новый `d3_touch.c`) раз в кадр
  читать `mgr = *(*(u64*)(main+0x1905620)+0xb80)` (проверить ненулевые, выровненные, в пределах guest-памяти),
  `focus = *(u64*)(mgr+0x50)`; опубликовать в атомик; JNI `nativeUiState()` → Java.
  Классификация по журналу: прогон `DM_D3_UIFOCUS=1` (лог при смене) через меню/инвентарь/скиллы/паузу/геймплей
  → таблица «UIID → экран»; хеши путей можно сверить, посчитав UIID путей из строк main тем же алгоритмом (0x347750).
* **B2 — observation-гейты на `*_Update`** (надёжнее, вкл. экраны без фокуса): по образцу OBS-таблицы
  `dm/tools/patch_nso.py:198-216` завести записи для build-id `2607a74f…` на входы `UIInventory_Console_Update` 0x1f66b0
  (`stp x29,x30`), `UISkills_Console_Update` 0x381b70, `UIPause_OnUpdate` 0x220f00, `UIConsole_MainMenu_OnUpdate` 0x362500,
  `UIConsole_Options_OnUpdate` 0x20b550, `WaypointMap_OnUpdate` 0x238270, `UIEquipmentManager_Console_Update` 0x1a2bf0,
  `UIConsoleParagon_Update` 0x212500, `UIFollower_Console_Update` 0x1e9390, `UIJournal_Console_Update` 0x209140,
  `UIConsole_ConversationOption_Updated` 0x20a010 … (первая инструкция каждого — из списка `tools/d3_ui_callbacks.py`;
  `adrp`/`b`/`ret`-входы, напр. 0x2c8630, 0x1740c0, 0x1c7870, 0x180fb0, гейтом не брать). Колбэк хоста:
  `screen_seen[id] = frame`; «меню открыто», если какой-то экран обновлялся ≤ 2 кадров назад. Нужен свободный номер OBS в
  `hle.h` и `DM_GAME_D3`-ветка подписки (сейчас `uimsg_subscribe` только `#ifndef DM_GAME_DOOM`, `front_android.c:38-45`).
* Риски B1: неверная цепочка указателей → чтение мусора (защита: проверка диапазона, только чтение); поток (2.5/4).
  Риски B2: правка патчера NSO и `equiv.py`-проверка; порядок/частота вызова `*_Update` (вызывается ли при скрытом экране).

### C1. Меню жестами (фаза 2, без RE)

Навигационный режим пада: прячутся кнопки скиллов, остаются B (назад) и плечи; на всём экране —
* свайп вверх/вниз/влево/вправо = D-pad (повтор при удержании после свайпа, как автоповтор клавиш), в кольцевых меню
  (инвентарь, D3 «кольца») = отклонение левого стика в сторону свайпа (кольцо выбирается направлением, `UIInventory_OnLeftStick`);
* тап = A, долгий тап = удержание A (D3 требует «держать» для некоторых действий), двойной тап = X (частое «вторичное» действие)
  — уточнить по подсказкам кнопок внизу экранов D3;
* касание у левого/правого края = L/R (табы), два пальца = B.
Это рабочая схема для **любых** экранов, включая свои диалоги игры, и не требует знать раскладку.

### C2. Тап по пункту = фокус + A (фаза 3, RE)

1. Рантайм-дамп (диагностика `DM_D3_UIDUMP=1` в хосте): обойти карту контролов `mgr+0` (узлы `{next, UIID, ctrl}`), для
   каждого `ctrl` выгрузить первые 0x200 байт + `vtable` в файл; сопоставить с известными путями (UIID из строк main) и
   скриншотами — найти поля прямоугольника, видимости, родителя, «фокусируемый». Помощник для статики: vtable+0x38/+0x40
   (фокус) уже известны из `UI_SetFocus`, хит-тест/рисование искать среди соседних слотов vtable.
2. Хит-тест в хосте на игровом потоке: точка тапа → координаты UI (с учётом `front_game_res`, safe zone `obj+0xa0`) →
   самый верхний видимый фокусируемый контрол.
3. Вызов `UI_SetFocus(&uiid)` (main+0x327dd0) из `dm_pad_hook` (как D2R вызывает игровые функции напрямую с игрового потока,
   `dm_world.c` / `dm_cursor.c:2937`), затем импульс A на следующий опрос (через существующую защёлку `hle_hid.c`).
4. Кольца и списки: если фокус ставится только на контейнер (2.5/3) — эмулировать выбор стиком/D-pad к нужному индексу
   (как D2R «ведёт» курсор стиком до прибытия, `dm_cursor.c:63-76`), индекс — из полей контрола списка (дамп).
Риски: assert в `UI_GetControl` (не звать), фокус на невидимом контроле, расхождение координат, обновления UI в середине
кадра. Тест: тапы `adb shell input tap` по пунктам главного меню/опций, сверка `mgr+0x50` и скриншота.

## 7. Фаза 3, шаг 1: устройство UI-контрола, дамп и API тапа (02.11.2026)

Статический разбор `work/exefs-update/main.raw` (capstone; Ghidra-сервер был недоступен), без телефона. Код:
`dm/host/hle_d3_ui.c` (только `DM_GAME_D3`), вызов из `hle_hid.c` `fill()` сразу после `dm_pad_hook`, JNI
`nativeD3UiTap` в `jni_android.c`, `DM_RUNTIME_DIR` (= каталог `dm/`) ставит `nativeStart`. Таблица имён: `tools/d3_uiid_names.py`
→ `work/d3-uiid-names.tsv` (34 484 id, 3,7 МБ).

### 7.1 UIID и имена (проверено)
* UIID = **FNV-1a 64** (offset `0xcbf29ce484222325`, prime `0x100000001b3`, main 0x6c90) по пути в нижнем регистре (`tolower`
  побайтно, 0x7ab0; PLT 0xc70f60 = `tolower`). Дочерний id = продолжение хеша родителя строкой `".<имя>"` (0x347360 → 0x6b20 с
  seed = id родителя) — то же, что хеш полного пути. Спец-id (таблица переходов 0xeba350): −3 `Main-Screen`, −2 `Root`, −1 «нет»,
  1 `Root.NormalLayer`, 2 `Root.WindowLayer`, 3 `Root.TopLayer` (константы 0xeba370…0xeba390 читает обход родителей 0x32f9xx).
* **Имён в рантайме нет**: `UIID_ToString` 0x347580 печатает 16 hex-цифр, `0x3474e0(dst, id, name)` = `*dst = id` (имя выброшено).
* Подтверждение алгоритма: в `UI/ConsolePause.ui` ссылка на контрол = `{u64 hash; u32 off; u32 size; u64 0}` (данные SNO с +0x10);
  поле имени `HardcoreSeasonalHeader` несёт `0x1aa38e6f5122abbd` = fnv("ConsolePause_main.LayoutRoot.HardcoreSeasonalHeader"), поле
  родителя через +0x18 — `0xf58a3f035f4eae78` = fnv("ConsolePause_main.LayoutRoot"). Пути в `.ui` — **относительно слоя**; слой берётся
  из строк main `Root.<Layer>.<Screen>_main…`, иначе все три. `tools/d3_uiid_names.py` восстанавливает так 16 676 относительных путей
  (с проверкой хеша) + 2 494 строки `Root.*` из main. Контролы, создаваемые в рантайме (элементы списков из шаблонов), остаются без имени.

### 7.2 Менеджер и карта (проверено)
`mgr = *(*(main+0x1905610+0x10) + 0xb80)` (GOT 0x114a840 → 0x1905610; рядом `+0xb78` = держатель UI-рендер-таргета, 0x12f030).

| mgr+ | что | где видно |
|---|---|---|
| 0x00 | карта `{u32 mask; u32 count; allocator; buckets @0x10}`, узел `{next; UIID; UIControl*}`, индекс = FNV-1a-32 по 4 младшим байтам id `& mask`; вставка без рехеша | 0x330000, вставка 0x332b70 (`count++` @+4, assert на дубликат) |
| 0x20 | id «захвата/наведения» (0x327a70 ставит и зовёт vtable+0xa0) | 0x327a70, 0x327b70 |
| 0x28 | **активный** контрол (0x327c00: старому vtable+0x20, новому +0x28; ставится, если `vtable+0x10 CanActivate`) | 0x327c00, ctor 0x390008 |
| 0x38 | ещё один id (модальный?) | 0x328280 / 0x328330 |
| 0x50 | **фокус** (`UI_SetFocus` 0x327dd0; `UI_GetFocus` 0x328180 возвращает `&mgr+0x50`, сбрасывая на −1, если контрола нет) | 0x327df0, 0x3281a0 |
| 0x58 | int | геттер/сеттер 0x327b90 / 0x327bb0 |

Ввод с геймпада в UI (0x32c4xx…0x32c9xx; `UI_GetFocus` зовут 119 мест): событие идёт **сфокусированному** контролу (клавиатурное —
активному `+0x28`) и всплывает к родителям; при скрытии контрол снимает с себя фокус (0x3904a0 → 0x327a70).

### 7.3 UIControl (проверено: конструктор 0x38fe40, `SetVisible` 0x390470, `UpdateVisibility` 0x390530, `UpdateRect` 0x3b31f0)

| +смещение | тип | смысл | доказательство |

| 0x88…0x94 | 4×float | **итоговый прямоугольник l, t, r, b в UI-единицах** (с якорями) | `UpdateRect` 0x3b3300…0x3b3408 |

| 0x160…0x18c | float | второй прямоугольник (тот же расчёт от `+0x180`), `+0x1a0…` — его прошлое значение | 0x3b3304…0x3b3388 |
| 0x1b4 | int | 3 = на весь экран (`0x3d9e0`) | 0x3b3208 |
| 0x1b8 / 0x1c0 | int | якорь по X / Y: 1 = левый/верхний край safe zone, 2 = правый/нижний | 0x3b3068…0x3b3190 |

**vtable** (слоты базового класса 0x10a6f28): +0x00/+0x08 деструкторы, **+0x10 CanActivate** (база 0x22d470 = 0; кнопки 0x38b370 =
`видим && (+0x3c8 & 0x20)`, 0x38f720 = `+0x1e8 && видим`, 0x38f960 = `видим && (+0x3c8 & 1)`), +0x20/+0x28 активирован/деактивирован,
**+0x38 / +0x40 потеря / получение фокуса** (база — пустые 0x22d4b0 / 0x22d4c0), +0x48 `Move(dx,dy)`, **+0x50 `SetVisible(bool)`**,

### 7.4 Координаты (проверено)
* UI-пространство **960×720** (0x34bc80: `ui.x = (px − R.l)·960/R.w`, `ui.y = (py − R.t)·720/R.h`; 960.0 @0xeb09e0, 720.0 @0xeb0e68).
  `R` = **`UI_PixelRect` 0x34baf0(float out[4])**: пиксельный прямоугольник вьюпорта (0x3d800, 0xa33730) по размеру рендер-таргета
  (`(*(g+0x10)+0xb78)+0x20` → vtable+0x28); если аспект ≠ 4/3 (±0.01), ширина = `trunc(H·4/3)` по центру.
* Размер окна в тех же пикселях: `gfx = *(main+0x1830f68)`, `+0x244` / `+0x248` (0x29a760; якоря `UpdateRect` считают от него).
* Якорь 1/2 переводит край safe zone (`mgr+0x1c` → 0x327770) в UI-единицы через 0x34bc80, поэтому у прижатых к краю контролов в
  широком кадре `ui.x < 0` или `> 960` — формула та же.
* В доли картинки: `px = R.l + ui·R.w/960`, `fx = px / W` (W, H из gfx). Хост берёт `R` вызовом 0x34baf0, только если его входы
  существуют (`*(g+0x10)+0xb78`, его `+0x20`, vtable внутри образа main), иначе считает `R` по формуле из W×H; что взято — в шапке
  дампа (`main 0x34baf0` / `4:3 formula`).

### 7.5 Поток (частично проверено)
Опрос пада идёт из главного кадра: main 0x40810 (главный цикл; его зовёт 0x4c84f0) → 0x40bf8 `bl 0x2b4230` → 0x2b43c8 `bl 0xf84b0` →
`bl 0xf7310` → `GetNpadStates` (HLE `fill()`). Тот же 0x40810 напрямую зовёт функции UI-менеджера (0x32dcb0; через 0x3ebc0 →
0x32e200/0x32de30/0x32ea30; через 0x3ee30 → 0x32dda0/0x333450). Значит чтение UI и вызов `UI_SetFocus` из `fill()` идут на главном
потоке игры между кадрами UI. Строка `[d3ui] on: … game thread tid N` — для сверки.

### 7.6 Что делает хост (`hle_d3_ui.c`)
* Все чтения — через `rd()`: кучу гостя и образ main копирует напрямую (диапазоны известны), остальное — `process_vm_readv` (плохой
  указатель = «нет данных», без падения). Контрол принимается, только если его vtable внутри образа main и `+0x30 == ключ узла`.
  Перед включением сверяются слова пролога 0x327dd0, 0x34baf0, 0x3b31f0 и GOT 0x114a840; на другом main — выключено с красной строкой.
* `DM_D3_UIDUMP=1`: каждый опрос пада читает `mgr+0x50` и `+0x28`, при смене — строка `[d3ui] focus <id> <имя> | active <id> <имя>`.
  Раз в 30 опросов проверяет `dm/ui-dump-now`; если есть — удаляет и пишет:
  * `dm/ui-dump.tsv`: шапка (число контролов, `mgr`, фокус, active, `+0x20`, размер окна и `R`), затем по строке на **видимый**
    (`+0x18` bit2) контрол: `id, name, vt` (смещение vtable в main), `type` (IsA-список), `flags, vis, shown, parent, layer` (3 Top /
    2 Window / 1 Normal / 0 иное), `depth, sib` (индекс в векторе детей родителя), `act` (CanActivate; −1 = неизвестный предикат),
    `fh` (свой OnFocusGained), `focus`, `ui_l..ui_b`, `px_l..px_b`, `fx_l..fx_b` (доли картинки), `extra` (у списка `sel first per n
    items=…`). `DM_D3_UIDUMP=2` — все контролы, включая невидимые.
  * `dm/ui-dump-raw.tsv`: `id, vt, hex` первых 0x400 байт каждого видимого контрола — для следующего шага RE (поля выбора, текст).
  * Имена — из `dm/ui-names.tsv` (грузится фоновым потоком при первом опросе).
* `DM_D3_UITAP=1` (по умолчанию выключено): `int dm_d3_ui_tap(float x, float y)` — доли картинки (0..1, левый верх), любой поток,
  только кладёт в очередь (атомики); 0 = выключено / вне 0..1. На ближайшем опросе пада: снимок карты, `ui = R⁻¹(x·W, y·H)`,
  кандидаты = видимые контролы с прямоугольником, содержащим точку, у которых `act == 1`, или свой OnFocusGained, или это список;
  «верхний» = больший слой, затем больший индекс среди братьев по пути от корня, затем глубже. Вызов **`UI_SetFocus(&id)`**:
  `void (*)(const uint64_t *)` по main+0x327dd0, единственный аргумент `x0` = указатель на 64-битный UIID, без `this` (менеджер
  берётся из глобала; если id уже в фокусе — ничего; иначе пишет `mgr+0x50`, у старого зовёт `vtable+0x38`, у нового `vtable+0x40`,
  контролы ищет сам и отсутствующий пропускает — assert 0x330000 не достигается). Затем A: пропуск одного опроса, 3 опроса с
  `DM_BTN_A`. Лог: `[d3ui] tap x,y = UI u,v -> id имя (type act fh list) focus old -> new`. `DM_D3_UITAP=2` — цель любой видимый
  контрол под пальцем (эксперименты).
* Проверка без фронтенда: файл `dm/ui-tap-now` с текстом `x y` (доли картинки) ставит тот же тап в очередь (раз в 30 опросов).
* JNI: `DmActivity.nativeD3UiTap(float x, float y) → boolean`; в Java объявить `static native boolean nativeD3UiTap(float x, float y);`
  и звать с `x = (touchX − picLeft)/picWidth`, `y = (touchY − picTop)/picHeight` (пока не подключено).

### 7.7 Риски и открытые вопросы
1. **Списки/кольца**: консольные экраны фокусируют контейнер (из 163 вызовов `UI_SetFocus` статически разрешились только списки и
   scroll-box'ы: `…AchievementList`, `…Talk.TalkList`, `…PlayerOptions…List.player_options`), выбор внутри — индекс `+0x1e0` списка.
   Тап по элементу ставит фокус на элемент/список, но **не меняет `sel`** — нужен метод выбора списка (следующий шаг: кто пишет
   `+0x1e0` в классе 0x10a65f0; дамп показывает `sel/items`).
2. «Табы» Inventory/Quests консольного меню могут вовсе не быть фокусируемыми контролами (переключение L/R) — смотреть `act`/`fh` в дампе.
3. Порядок отрисовки в `above()` — предположение «слой, затем порядок детей»; модальные окна в том же слое могут перекрываться иначе.
4. Вызов 0x34baf0 из хоста читает опции и рендер-таргет; защищён проверкой указателей, при сомнении — формула 4:3.
5. `process_vm_readv` в приложении: при отказе (не EFAULT) — одна строка в лог, читаются только куча и образ.
6. A после фокуса: если экран обрабатывает A по своему индексу, а не по фокусу, сработает прежний пункт.

### 7.8 Как снимать
1. Имена: `work/d3-uiid-names.tsv` уже сделан (`python tools/d3_cpk.py mextract work/romfs <tmp>/ui 'UI/*.ui'`, затем
   `python tools/d3_uiid_names.py work/exefs-update/main.raw <tmp>/ui/UI > work/d3-uiid-names.tsv`); залить как `dm/ui-names.tsv`.
2. `dm/env`: `DM_D3_UIDUMP=1` (или `=2` для всех контролов), для пробы тапа ещё `DM_D3_UITAP=1`.
3. На каждом экране: скриншот, `touch dm/ui-dump-now`, ~1 с, забрать `dm/ui-dump.tsv` и `dm/ui-dump-raw.tsv` с именем экрана.
   Экраны: главное меню; выбор героя; пауза (+); консольное меню (−) на вкладках Inventory и Quests/Journal (L/R); навыки; опции;
   диалог с NPC; геймплей без меню.
4. Между экранами — строки `[d3ui] focus …` в `boot.log` / logcat при навигации D-pad'ом.
5. Тап: `echo "0.31 0.12" > dm/ui-tap-now` по долям из `fx_*` нужного контрола в дампе → строка `[d3ui] tap …` + скриншот.
